# 第四章 大语言模型智能体辅助设计系统

本章研究大语言模型智能体在实验拓扑配置与基础模块扩展中的辅助作用，分析其工具调用机制、知识表示方式、代码生成流程及操作约束，并提出仿真反馈驱动的工具自迭代设计。智能体不参与 FPGA 实时反馈环路。

## 4.1 设计动机与总体架构

### 4.1.1 自然语言辅助配置的需求

第二章所述路由矩阵允许在运行时配置模块连接，但可选连接数量随端口规模增加。第三章的节点编辑器提供拓扑可视化及信号类型检查，具体模块选择和端口匹配仍需要领域知识。

以 PDH 锁定为例，用户给出的控制目标需要进一步分解为模块实例、端口连接和参数配置。本章将这一转换表示为

$$
\text{自然语言意图} \xrightarrow{\text{LLM + 工具调用}} \text{画布拓扑} \xrightarrow{\text{第三章映射}} \text{路由寄存器配置}
$$

物理参数到寄存器配置的映射与画布拓扑到硬件连接的映射分别在第二、三章讨论。本章首先研究自然语言意图到画布拓扑的转换，再讨论新模块生成与验证的扩展路径。

### 4.1.2 分层结构

智能体系统由七个功能层次构成，各层职责如表所示。

| 层次 | 主要职责 |
|------|----------|
| 交互层 | 呈现用户请求、模型响应和工具执行结果 |
| 编排层 | 管理对话上下文、函数调用循环与后台任务 |
| 接口层 | 封装兼容 Chat Completions 的模型服务接口 |
| 工具层 | 声明工具参数结构并分发调用 |
| 隔离层 | 将结构化参数转换为画布操作，并实施前置校验 |
| 知识层 | 提供模块端口、参数及典型拓扑的结构化描述 |
| 生成层 | 根据模块规格生成硬件与软件框架 |

层间依赖是单向的：交互层仅与编排层通信，编排层经工具层操作隔离层，隔离层是唯一接触 Qt 对象的环节。知识层为编排层提供系统提示词中的模块描述，为工具层提供模块元数据查询。

系统入口通过 Qt 信号槽连接聊天面板与智能体编排层，分别传递用户输入、模型响应、工具执行结果和错误状态。该集成方式使智能体功能可以独立启用或停用，并保持现有手动配置流程的可用性。

## 4.2 工具层与错误反馈

### 4.2.1 工具集合

智能体通过九类工具查询或修改画布。工具参数以 JSON Schema 声明，并由统一的分发机制映射到画布操作：

| 工具 | 作用 | 关键参数 |
|------|------|---------|
| `list_modules` | 列出可用模块类型与画布现状 | `scope`: available / on_canvas / both |
| `get_module_info` | 查询单个模块的端口与参数详情 | `module_type` |
| `create_module` | 在画布上创建模块节点 | `module_type`, `position_x/y`, `params` |
| `connect_modules` | 建立端口间连线 | `source_node`, `source_port`, `destination_node`, `destination_port` |
| `disconnect_module` | 断开输入端口或删除节点 | `node_name`, `port_index`（省略则删除节点） |
| `set_parameter` | 设置模块参数 | `node_name`, `params` |
| `auto_layout` | 自动布局 | 无 |
| `generate_module` | 生成新模块类型的代码 | `module_name`, `inputs`, `outputs`, `params` |
| `clear_canvas` | 清空画布 | `confirm`（必须显式为真） |

工具接口区分查询与修改操作。模块查询为只读，连线前可用于取得端口索引与信号类型；清空画布操作要求显式确认参数，以减少由模型误判引发的意外清空。该约束的有效性需要通过边界测试验证。

### 4.2.2 错误作为反馈

工具分发层将可捕获的执行异常转换为包含工具名称和错误原因的结构化结果；画布隔离层则返回执行状态及相应数据。这一机制使失败信息能够进入后续对话上下文，同时避免已处理的异常直接传播至 Qt 事件循环。

错误结果包括端口越界、输入端口占用、未知模块类型和实例数超限等信息，分别提供合法范围、冲突位置或可查询的模块列表。结果作为工具消息加入对话历史，使模型能够依据失败原因调整下一轮操作。该反馈机制是否提高任务成功率，需要比较首次生成与允许纠错后的最终结果。

已覆盖的校验错误由工具层返回；未覆盖的参数边界与异常传播仍需进一步测试。

### 4.2.3 门面隔离

画布隔离层是智能体与图形界面之间的调用边界，以结构化参数和结果封装画布操作。其作用体现在三个方面。

**类型边界。** 模型以 JSON 传递节点标识、端口索引和坐标；隔离层将其转换为 Qt 画布对象，并返回可序列化的执行结果。

**前置校验。** 连线前检查节点存在性、端口索引范围及目标输入端口的占用情况。通过检查后，画布层继续执行第 3.4.2 节的信号类型约束。参数取值范围的校验仍不完整，见第 4.7 节。

**能力边界。** 智能体接口只提供画布编辑操作，未提供串口直通或寄存器裸写工具。模块实例上限与复合模块展开仍由既有画布逻辑处理。

## 4.3 编排层与函数调用循环

### 4.3.1 循环结构

编排层将用户请求加入对话历史，并在后台线程中执行函数调用循环。主要步骤如下：

1. 以当前消息列表与工具声明请求模型；
2. 将模型返回的助手消息（含文本与 `tool_calls`）追加至历史；
3. 若无 `tool_calls`，返回文本，循环结束；
4. 否则顺序执行每个工具调用，将结果以 `role: "tool"` 消息追加至历史；
5. 调用一次 `auto_layout` 整理版面；
6. 回到第 1 步。

模型根据工具结果决定后续调用，直至给出最终答复或达到迭代上限。其中第 5 步的自动布局是便利性设计——模型创建节点时若未指定坐标，门面以 `_next_auto_position` 顺次向右排布，循环末尾的分层布局则将其整理为符合信号流向的版面。布局失败不会中断拓扑编辑，但应在后续版本中记录该异常以便诊断。

### 4.3.2 迭代上限

循环的最大迭代次数设为 15。达到上限时，系统终止本轮工具调用并向用户返回状态说明。

这一机制针对的是函数调用式智能体的典型失效模式：模型在工具结果不符预期时反复尝试同类调用而不收敛。设定上限使单次请求的开销有界——每次迭代对应一次模型 API 调用，无上限的循环在失效时既消耗配额又可能持续改动画布。

上限值的选取需权衡。搭建一个完整 PDH 拓扑需要约 5 个 `create_module` 与 9 个 `connect_modules` 调用；由于模型可在单轮中并行返回多个 `tool_calls`，循环的迭代次数通常远少于工具调用总数，15 轮对该规模的任务有相当余量。但对于更复杂的拓扑，该值可能偏紧，此时上限消息提示用户检查画布并续发指令，而非使系统陷入沉默。

### 4.3.3 线程模型与错误处理

模型服务调用为阻塞式网络请求。为维持界面响应，函数调用循环运行于 Qt 工作线程，并通过信号将工具状态与结果传递至主线程。

错误处理分两级。模型 API 层面的失败（网络异常、认证失败、非 200 响应）由 `LLMClient` 转换为 `LLMError` 抛出，在循环内被捕获后转为一条用户可见的错误消息并终止循环，而非使线程崩溃。工作线程的 `run` 方法则以 `try/except` 兜底捕获一切未预期异常，经 `error` 信号报告并附完整 traceback——此处保留 traceback 是有意的，因为这类异常意味着程序缺陷而非使用错误，调试信息对开发有价值。

### 4.3.4 接口层的服务端中立性

接口层封装兼容 Chat Completions 的请求格式，传递对话历史、模型参数及工具声明。模型服务地址与模型名称可由用户配置。

采用兼容接口使系统能够适配实现相同调用格式的模型服务；不同服务的工具调用行为仍需分别测试。`temperature` 默认取 0.1 的较低值，因为本场景需要的是对工具规格的准确遵循，而非表达的多样性。

当前模型服务凭据由本地配置文件保存。后续应改用环境变量或系统凭据存储，并检查配置文件的版本控制规则。

## 4.4 模块知识库

### 4.4.1 结构化模块描述

模型需要知道系统有哪些模块、各模块的端口语义与参数含义，才能生成合理的拓扑。`module_registry.py` 以三个字典承载这一知识：

- `MODULE_REGISTRY`——12 个基础模块：PID 控制器、累加器、三角函数运算器、反三角函数运算器、线性缩放器、FIR 滤波器、IIR 滤波器、线性变换器、混频器、解卷绕器、PDH 状态机、LO 自动校准状态机；
- `COMPOSITE_MODULES`——2 个复合模块：正弦波发生器、数字控制振荡器，各自展开为若干基础模块及其内部连线；
- `SPECIAL_NODES`——2 个常量节点：布尔值真、布尔值假，用于为控制输入提供固定电平。

每个条目记录显示名、内部短名列表、实例数上限、类别、用途说明，以及输入输出端口的索引、名称、显示名与信号类型。参数分为 `direct_params`（单寄存器直写）与 `indirect_params`（多寄存器原子写入）两类，与第三章 3.2.1 节的参数字典体系对应。

知识库与第三章的 `qt_module.py` 存在信息重叠，这是一处需要指出的设计代价：模块的端口定义在两处各有一份，新增模块时须同步维护，否则智能体会依据过时信息生成非法连线。更稳健的做法是由单一来源自动导出，`code_generator.py` 的运行时注册机制（见 4.5.2 节）已部分缓解该问题，但既有模块的两份描述仍需人工保持一致。后续应建立启动时的一致性校验，比较两处端口定义并报告差异。

### 4.4.2 上下文构建与拓扑范式

`build_llm_context` 将上述字典格式化为 Markdown 文本，注入系统提示词的 `{module_descriptions}` 占位符。输出内容依次为基础模块（含全部端口与信号类型）、常量节点、复合模块、系统 IO 边界端口（输入通道 A–H 对应 ADC，输出通道 A–H 对应 DAC），最后可选附加 `PDH_LOCKING_PATTERN`。

知识库中的 PDH 参考拓扑按五类连接组织：信号生成链（累加器 → 三角函数）、误差信号链（三角函数余弦输出 → 混频器参考端，探测器信号 → 混频器信号端）、反馈链（混频器 → PID → 累加器误差输入）、状态机控制（PDH 状态机的三路复位控制分别门控 PID、混频器与累加器，累加器快速输出回授状态机的扫描输入）、输出监测（累加器与 PID 输出接至 DAC 通道）。

注入该范式的理由是：PDH 锁定是本系统的主要应用场景，其拓扑在领域内固定且端口对应关系琐碎易错。将其作为参考清单写入提示词，使模型在处理最常见请求时有确定依据，而不必从端口语义逐步推断。这本质上是以领域知识换取可靠性——代价是提示词与范式耦合，若硬件端口分配变更，该常量须同步更新。

## 4.5 代码生成与能力边界

### 4.5.1 生成流程

`generate_module` 工具针对的场景是：用户需要的模块类型在系统中不存在。`CodeGenerator.generate` 接收模块名、显示名、描述、输入输出端口列表与参数列表，产出六类文件：

| 产物类别 | 作用 |
|----------|------|
| VHDL 运算内核骨架 | 定义端口、参数接口与缓冲结构 |
| VHDL 模块封装 | 对接总线和参数存储 |
| Python 硬件类 | 将寄存器配置封装为模块参数 |
| Python 节点类 | 提供画布端口与参数编辑能力 |
| 参数模式 | 描述参数类型及默认值 |
| 端口分配记录 | 保存数据与控制端口编号 |

生成过程中有两项自动推导。其一是参数 RAM 深度：按参数个数向上取到不小于 8 的 2 的幂，再乘 32 位得到总位宽，与第二章 2.4.2 节的参数 RAM 结构对应。其二是端口号分配：`_alloc_ports` 依据输入输出的信号类型分别在数据通道与布尔通道的端口空间中分配编号，并持久化记录以避免重复占用——这直接对应第二章路由矩阵的端口编号体系。

### 4.5.2 运行时注册

`register_runtime` 以运行时打补丁的方式将生成的模块注入正在运行的应用：向 `module_factory` 字典登记节点类、扩展端口号解析函数、更新组件面板。这使新生成的 Python 侧模块无需重启即可用于 `create_module`。

### 4.5.3 能力边界

代码生成功能的适用范围由生成产物及其运行条件决定。

**生成的 VHDL 内核是骨架而非实现。** 代码生成器的返回值中显式包含这一说明：实体声明、端口定义、参数 RAM 接口、输入输出缓冲与总线封装完整且可综合，但 `use_input_buffer` 与 `use_output_buffer` 之间的信号处理主体留空，须由硬件工程师填写。换言之，生成器自动化的是模块的**外壳与接口**——这部分在本系统中高度模式化（第三章 3.2 节所述的"内核 + 总线封装 + 参数 RAM"统一骨架），因而适合模板化生成；而算法主体涉及定点格式选择、流水线划分与时序收敛，不是模板所能覆盖的。

**新模块需要重新综合才能真正可用。** 运行时注册仅使 Python 侧的节点类生效，画布上可以放置该模块、可以连线、可以设参数，但 FPGA 中并不存在对应的硬件逻辑。真正可用须经填写内核、重新综合实现、下载比特流三步。因此该功能的实际价值在于**加速模块开发的样板代码环节**，而非实现"自然语言直接生成可运行硬件"。

因此，生成结果仍需完成算法实现、仿真验证与时序分析，不能直接视为可运行硬件模块。

## 4.6 仿真反馈驱动的工具自迭代设计

### 4.6.1 闭环生成与验证流程

针对第 4.5 节中运算内核仍需人工实现的问题，本文进一步设计由生成、验证、修正与封装组成的工具级自迭代闭环。其输入为结构化模块规格，包括功能定义、端口及位宽、时钟与复位方式、定点格式、目标时序约束和测试用例。大语言模型依据该规格生成基础模块的 RTL 实现及相应测试平台，并将候选代码置于独立的工程目录中。结构化规格同时作为验证基准，以避免后续修正偏离原始功能要求。

验证环节通过 Vivado 自动化接口调用编译、展开与行为仿真，收集编译日志、测试断言和波形数据。功能判定以模块规格规定的测试用例及独立参考结果为依据，并结合波形检查复位、握手及关键状态转移，避免以候选代码自身的输出作为正确性标准。时序判定则依据综合与实现后的静态时序分析报告；行为仿真中的波形正确并不等价于目标器件上的时序收敛。对于资源占用敏感的模块，还应将资源利用率纳入验收条件。

### 4.6.2 基于 ReAct 的修正与停止条件

当编译、功能或时序检查失败时，系统将错误类别、对应日志、失配波形位置及关键路径信息组织为观察结果，反馈给智能体。智能体按照“分析原因—修改 RTL—重新验证”的 ReAct 过程生成下一版候选模块，不得通过修改验收用例消除失配。修正仅作用于当前候选版本；每轮保存模块规格、代码版本、工具配置与验证结果，以便定位回归错误并复现实验。

设第 $i$ 轮候选代码为 $C_i$，验证反馈为 $E_i$，则迭代过程可表示为 $C_{i+1}=F(C_i,E_i)$。只有功能测试通过且预设的时序与资源约束得到满足时，候选模块才进入封装阶段。若达到迭代上限或连续修正未能消除错误，流程终止并保留失败记录，由人工检查模块规格、测试平台或实现方案。该条件防止智能体将未通过验证的候选代码直接纳入工具集合。

### 4.6.3 工具封装与能力边界

通过验证的 RTL 模块与第 4.5 节所述的总线封装、参数模式、Python 硬件类和画布节点类关联，形成具有明确端口、参数及验证记录的候选工具。候选工具经注册后可为后续模块生成或拓扑设计提供可复用的能力；新增工具又可作为下一轮设计任务的构件，从而构成工具集合的递归扩展。本文所称工具级自迭代，即这一受验证条件约束的能力积累过程，并不涉及大语言模型参数的自主更新。

该闭环属于系统设计，现有代码生成功能尚未完成 Vivado 自动验证与修正流程的集成。即使候选模块通过仿真和静态时序检查，仍须经过系统级集成、比特流生成及板级测试，才能认定其可用于实际 FPGA 控制平台。闭环的收敛率、平均迭代次数与工具复用效果也需在固定任务集上另行评估。

## 4.7 可靠性边界

针对现有画布编辑路径，智能体层的操作约束由多道校验机制叠加构成。按模型输出的流经顺序：

| 层次 | 约束机制 | 阻止的失效 |
|------|---------|-----------|
| 接口层 | 工具 JSON Schema 的 `required` 与类型声明 | 参数缺失、类型错误 |
| 工具层 | 统一异常捕获，错误转结构化返回 | 异常穿透至事件循环 |
| 工具层 | `clear_canvas` 显式确认 | 误清空画布 |
| 隔离层 | 节点存在性与端口索引范围校验 | 越界访问、空引用 |
| 隔离层 | 输入端口独占性检查 | 多驱动冲突 |
| 隔离层 | 仅暴露画布操作，无串口直通 | 绕过协议层的任意硬件写入 |
| 既有层 | 信号类型检查（第三章 3.4.2 节） | 物理含义错误的连线 |
| 既有层 | 实例数上限（`_alloc_index`） | 超出硬件可用模块数 |
| 编排层 | 迭代上限 15 轮 | 不收敛的工具调用循环 |

其中，门面的能力边界限制了模型对运行中硬件的直接操作，既有类型检查则继续约束画布连线。这些机制限制了模型可调用的操作范围，但参数校验与异常处理尚有缺口，不能据此断言所有错误都只影响画布。

仍需指出两处尚未解决的薄弱环节。其一，`set_parameter` 的参数值校验依赖各节点类的 `set_params` 实现，智能体层本身不做范围检查，若某模块的实现对越界值未作防护，模型可能写入非法参数。其二，门面在节点创建后的参数应用失败时未返回完整错误状态，这会使"模块已创建但参数未生效"的状态对模型不可见，可能导致后续推理建立在错误前提上。两者均建议改进，后者的修正尤为直接：将参数应用结果并入返回字典即可。

## 4.8 本章小结

大语言模型智能体通过受限工具编辑画布，利用结构化错误反馈调整操作，并由知识库提供模块语义。针对新模块开发，本文进一步提出基于 Vivado 验证反馈的工具自迭代闭环，以功能、时序和资源约束控制候选模块的封装与复用。现有实现的有效性，以及新增闭环的收敛性和硬件适用性，仍需分别通过交互记录、自动化验证与板级测试予以评估。
