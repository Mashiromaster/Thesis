# 第七章 智能体辅助设计系统

前五章完成了从物理原理到硬件实现、再到上位机软件的完整链路。至此系统已可用，但"可用"与"易用"之间仍有距离：第五章的路由矩阵赋予了系统运行时任意重构信号链路的能力，而要真正用好这一能力，用户须同时掌握 14 种模块的端口语义、四类信号的兼容规则、各模块的参数含义与物理量换算关系。这构成了一道不低的门槛——硬件的灵活性被操作的复杂性部分抵消。

本章介绍为降低这一门槛而设计的智能体辅助设计层。其目标是使实验拓扑可由自然语言描述直接生成：用户陈述意图，模型调用工具操作画布，而画布的每一次改动又直接对应硬件路由寄存器的写入。该层位于第六章软件体系之上，是全系统最顶层的交互入口，代码位于 `FPGA_Agent/` 目录，共 11 个模块约 3300 行。

需要先行说明本章的性质。智能体层解决的是**人机交互效率**问题，不参与控制回路的实时运算，因此其设计目标与前几章截然不同：第五章的 RTL 设计以时序收敛与延迟为第一约束，而本层的核心约束是**可靠性边界**——如何让一个输出本质上不确定的语言模型去操作一套真实硬件的配置界面，且保证最坏情况下不会损坏系统状态。这一约束塑造了本章几乎全部的架构决策。

## 7.1 设计动机与总体架构

### 7.1.1 从"可重构"到"易重构"

第五章指出，路由矩阵把拓扑从设计时常量变成了运行时变量。但变量的取值空间极大：$64\times64$ 的交叉矩阵在原理上允许的连接组合数远超人工枚举的能力，而其中物理上有意义的组合只占极小一部分。第六章的节点编辑器通过可视化与类型检查压缩了这一空间，使非法连接在连线阶段即被拒绝；然而它仍然要求用户**知道自己要连什么**。

实际实验场景中，用户的意图往往是目标导向而非步骤导向的——"搭一个 PDH 锁定环路"是一句完整的需求陈述，但把它翻译为"创建累加器、三角函数运算器、混频器、PID 控制器、PDH 状态机五个模块，再按九条特定的端口对应关系连线，并设置调制频率与增益"则需要相当的领域知识。智能体层正是填补这一翻译环节：

$$
\text{自然语言意图} \xrightarrow{\text{LLM + 工具调用}} \text{画布拓扑} \xrightarrow{\text{第六章映射}} \text{路由寄存器配置}
$$

右侧两个箭头在第五、七章已经建立，本章补上最左侧的箭头。

### 7.1.2 分层结构

智能体层自身划分为五个层次，各层职责与对应文件如下表。

| 层次 | 文件 | 行数 | 职责 |
|------|------|------|------|
| 交互层 | `agent_chat_widget.py` | 316 | 聊天面板，消息气泡、工具调用折叠展示、设置对话框 |
| 编排层 | `agent_core.py` | 267 | 函数调用循环、对话历史管理、后台线程调度 |
| 接口层 | `llm_client.py` | 141 | OpenAI 兼容 `/chat/completions` 协议封装 |
| 工具层 | `tool_definitions.py` / `tool_executor.py` | 381 / 170 | 工具的 JSON Schema 声明与分发执行 |
| 隔离层 | `canvas_bridge.py` | 366 | 画布操作门面，隔离 Qt 内部结构 |
| 知识层 | `module_registry.py` | 678 | 模块知识库与 LLM 上下文构建 |
| 生成层 | `code_generator.py` | 716 | 新模块的 VHDL + Python 代码生成 |

层间依赖是单向的：交互层仅与编排层通信，编排层经工具层操作隔离层，隔离层是唯一接触 Qt 对象的环节。知识层为编排层提供系统提示词中的模块描述，为工具层提供模块元数据查询。

值得说明的是 `main.py`（126 行）的组装方式。该入口直接实例化既有的 `MainWindow`，再将聊天面板以 `addDockWidget` 停靠于右侧，并通过 Qt 信号槽完成双向连接：

```
chat.user_message_submitted  →  agent.send_message
agent.response_ready         →  chat.add_assistant_message
agent.tool_executed          →  chat.add_tool_call
agent.thinking_started/stopped → chat.set_thinking
agent.error_occurred         →  chat.add_system_message
```

这一组装**未修改第六章的任何既有代码**。智能体层是纯增量的旁挂模块，`qt_ui_mainwindow.py` 对其存在无感知。这一点在工程上有实际价值：智能体功能可以独立启用或禁用，出现问题时可直接回退到第六章的纯手动界面，而不影响系统的基本可用性。

## 7.2 工具层设计

### 7.2.1 工具集合

智能体对画布的全部操作能力由九个工具构成，以 OpenAI 函数调用的 JSON Schema 格式声明于 `tool_definitions.py`，由 `ToolExecutor` 的分发表（`tool_executor.py:21-31`）映射到具体实现：

| 工具 | 作用 | 关键参数 |
|------|------|---------|
| `list_modules` | 列出可用模块类型与画布现状 | `scope`: available / on_canvas / both |
| `get_module_info` | 查询单个模块的端口与参数详情 | `module_type` |
| `create_module` | 在画布上创建模块节点 | `module_type`, `position_x/y`, `params` |
| `connect_modules` | 建立端口间连线 | `source_node`, `source_port`, `destination_node`, `destination_port` |
| `disconnect_module` | 断开输入端口或删除节点 | `node_name`, `port_index`（省略则删除节点） |
| `set_parameter` | 设置模块参数 | `node_name`, `params` |
| `auto_layout` | 自动布局 | 无 |
| `generate_module` | 生成新模块类型的代码 | `module_name`, `inputs`, `outputs`, `params` |
| `clear_canvas` | 清空画布 | `confirm`（必须显式为真） |

工具集合的划分遵循两条原则。其一是**查询与修改分离**：`list_modules` 与 `get_module_info` 为只读，模型被提示词要求在连线前先查询端口索引与信号类型，以此减少盲目尝试。其二是**危险操作显式确认**：`clear_canvas` 要求参数 `confirm` 为真，否则返回错误而不执行（`tool_executor.py:167-170`）。这使模型无法因一次措辞歧义的用户请求而意外清空用户正在编辑的拓扑。

### 7.2.2 错误作为反馈

工具层的一个核心设计是：**所有失败都以结构化结果返回，而非抛出异常**。`ToolExecutor.dispatch` 以统一的异常捕获包裹每次调用：

```python
try:
    result = handler(args)
    ...
except Exception as e:
    return json.dumps({"error": str(e), "tool": tool_name},
                      ensure_ascii=False)
```

隔离层的每个方法同样返回 `{"success": bool, ...}` 形式的字典而非抛异常。这一约定带来两个后果。

第一，错误信息成为模型的输入。错误文本被刻意写成可据以纠正的形式，而非仅标明失败。例如端口索引越界时返回合法范围（`canvas_bridge.py:165-172`）：

> `"Source port index 5 out of range (0-2)."`

输入端口已被占用时则同时给出补救动作：

> `"Port In2 of 'PIDC' already has a connection. Disconnect it first."`

模块类型不存在时给出查询途径：

> `"Unknown module type: 'XXX'. Use list_modules to see available types."`

实例数超限时报告具体上限：

> `"Max instances (2) reached for 'PID控制器'."`

由于这些字符串会以 `role: "tool"` 消息进入对话历史，模型能够读取并在下一轮调整调用——系统提示词第 7 条即明确要求"若工具调用失败，仔细阅读错误信息，诊断问题，尝试替代方案"。错误信息因此从调试输出转变为**控制信号**，这是函数调用式智能体与传统 API 的一个本质差异：接口的措辞直接影响系统的行为质量。

第二，异常不会穿透到 Qt 事件循环。无论模型生成何种非法参数，最坏结果都是画布不变而对话中出现一条错误记录。

### 7.2.3 门面隔离

`CanvasBridge` 是智能体与图形界面之间的唯一通道，提供 13 个公开方法，全部以字典入出参。其隔离作用体现在三个方面。

**类型边界。** 模型的输出是 JSON，而画布操作需要 `QPointF`、`QGraphicsItem`、`NodeItem`、`PortItem` 等 Qt 对象。门面承担了全部转换：节点以字符串内部名标识，经 `_find_node` 遍历场景项查找（`canvas_bridge.py:124-130`）；端口以零基整数索引标识，经 `node.out_ports[idx]` / `node.in_ports[idx]` 解析；坐标以数值对传入，在门面内构造为 `QPointF`。模型因此无需也无法持有任何 Qt 对象引用。

**前置校验。** 连线操作在触及场景之前完成四项检查：源节点存在、目标节点存在、源端口索引在 `out_ports` 范围内、目标端口索引在 `in_ports` 范围内，随后检查目标端口是否已有连接。只有全部通过才调用 `scene.create_connection`，而该方法内部仍会执行第六章 6.4.2 节的信号类型检查——**类型安全机制对智能体同样生效**，模型不能绕过它。这一点值得强调：智能体层并未因追求自动化而削弱既有的安全约束，相反，它继承了全部约束并在其上叠加了参数级校验。

**能力边界。** 门面只暴露画布编辑所需的操作，不提供串口直通、寄存器裸写、文件系统访问等接口。模型可以改变拓扑与参数，但无法越过第六章的协议层直接向硬件发送任意命令。实例数上限由既有的 `view._alloc_index` 把关（返回 `None` 即超限），复合模块经 `composite_cls.create_sub_modules` 展开，两者均复用第六章的既有逻辑而非另行实现。

## 7.3 编排层与函数调用循环

### 7.3.1 循环结构

`AgentCore.send_message` 接收用户文本，追加至对话历史，随后在 `_AgentWorker`（`QThread` 子类）中启动函数调用循环。循环体的逻辑为（`agent_core.py:203-267`）：

1. 以当前消息列表与工具声明请求模型；
2. 将模型返回的助手消息（含文本与 `tool_calls`）追加至历史；
3. 若无 `tool_calls`，返回文本，循环结束；
4. 否则顺序执行每个工具调用，将结果以 `role: "tool"` 消息追加至历史；
5. 调用一次 `auto_layout` 整理版面；
6. 回到第 1 步。

这是一个标准的 ReAct 式循环：模型观察工具结果，据此决定下一步动作，直至不再需要工具而给出最终答复。其中第 5 步的自动布局是便利性设计——模型创建节点时若未指定坐标，门面以 `_next_auto_position` 顺次向右排布，循环末尾的分层布局则将其整理为符合信号流向的版面。该调用被置于 `try/except` 中静默忽略失败，因为布局失败不应中断功能性操作。

### 7.3.2 迭代上限

循环的迭代次数由配置项 `max_tool_iterations` 限制，默认 15（`config.json`）。达到上限时不静默截断，而是向对话追加一条说明消息并返回：

> 已达到最大工具调用次数 (15)。我已完成了 15 步操作，请检查画布结果。

这一机制针对的是函数调用式智能体的典型失效模式：模型在工具结果不符预期时反复尝试同类调用而不收敛。设定上限使单次请求的开销有界——每次迭代对应一次模型 API 调用，无上限的循环在失效时既消耗配额又可能持续改动画布。

上限值的选取需权衡。搭建一个完整 PDH 拓扑需要约 5 个 `create_module` 与 9 个 `connect_modules` 调用；由于模型可在单轮中并行返回多个 `tool_calls`，循环的迭代次数通常远少于工具调用总数，15 轮对该规模的任务有相当余量。但对于更复杂的拓扑，该值可能偏紧，此时上限消息提示用户检查画布并续发指令，而非使系统陷入沉默。

### 7.3.3 线程模型与错误处理

模型 API 调用是阻塞的网络请求，单次耗时可达数秒至数十秒（`llm_client.py` 中 `timeout` 默认 120 秒）。若在 Qt 主线程执行，界面将完全冻结。因此循环置于 `QThread` 工作线程，与界面的通信全部经 Qt 信号完成：`tool_call_started`、`tool_call_finished`、`finished`、`error` 四个信号跨线程投递至主线程的槽函数。界面因此在模型"思考"期间保持响应，并以动态省略号提示状态（`agent_chat_widget.py:252`）。

错误处理分两级。模型 API 层面的失败（网络异常、认证失败、非 200 响应）由 `LLMClient` 转换为 `LLMError` 抛出，在循环内被捕获后转为一条用户可见的错误消息并终止循环，而非使线程崩溃。工作线程的 `run` 方法则以 `try/except` 兜底捕获一切未预期异常，经 `error` 信号报告并附完整 traceback——此处保留 traceback 是有意的，因为这类异常意味着程序缺陷而非使用错误，调试信息对开发有价值。

### 7.3.4 接口层的服务端中立性

`llm_client.py` 实现的是 OpenAI 兼容的 `/chat/completions` 协议，其请求体仅包含 `model`、`messages`、`temperature`、`max_tokens` 四个基本字段，工具声明以 `tools` 与 `tool_choice: "auto"` 传递。端点地址、模型名与密钥均来自配置文件，且可在运行时经设置对话框修改（`agent_chat_widget.py:258-310`）。

选择这一协议而非绑定特定厂商 SDK 的考虑是：该协议已成为事实标准，多数商业服务与本地推理框架均提供兼容接口。系统因此可在不同模型服务间切换而无需改动代码。`temperature` 默认取 0.1 的较低值，因为本场景需要的是对工具规格的准确遵循，而非表达的多样性。

此处需明确一项安全考量：`config.json` 中的 `api_key` 字段以明文存储于仓库目录内。该文件须排除在版本控制之外，否则密钥将随代码提交而泄露。【待核实】当前仓库的 `.gitignore` 是否已包含该文件，若未包含须立即补上，并建议改为从环境变量读取。

## 7.4 知识层：模块知识库

### 7.4.1 结构化模块描述

模型需要知道系统有哪些模块、各模块的端口语义与参数含义，才能生成合理的拓扑。`module_registry.py` 以三个字典承载这一知识：

- `MODULE_REGISTRY`——12 个基础模块：PID 控制器、累加器、三角函数运算器、反三角函数运算器、线性缩放器、FIR 滤波器、IIR 滤波器、线性变换器、混频器、解卷绕器、PDH 状态机、LO 自动校准状态机；
- `COMPOSITE_MODULES`——2 个复合模块：正弦波发生器、数字控制振荡器，各自展开为若干基础模块及其内部连线；
- `SPECIAL_NODES`——2 个常量节点：布尔值真、布尔值假，用于为控制输入提供固定电平。

每个条目记录显示名、内部短名列表、实例数上限、类别、用途说明，以及输入输出端口的索引、名称、显示名与信号类型。参数分为 `direct_params`（单寄存器直写）与 `indirect_params`（多寄存器原子写入）两类，与第六章 6.2.1 节的参数字典体系对应。

知识库与第六章的 `qt_module.py` 存在信息重叠，这是一处需要指出的设计代价：模块的端口定义在两处各有一份，新增模块时须同步维护，否则智能体会依据过时信息生成非法连线。更稳健的做法是由单一来源自动导出，`code_generator.py` 的运行时注册机制（见 7.5.2 节）已部分缓解该问题，但既有模块的两份描述仍需人工保持一致。【待补充】建议补充一致性校验脚本，在启动时比对两处定义并在不一致时告警。

### 7.4.2 上下文构建与拓扑范式

`build_llm_context` 将上述字典格式化为 Markdown 文本，注入系统提示词的 `{module_descriptions}` 占位符。输出内容依次为基础模块（含全部端口与信号类型）、常量节点、复合模块、系统 IO 边界端口（输入通道 A–H 对应 ADC，输出通道 A–H 对应 DAC），最后可选附加 `PDH_LOCKING_PATTERN`。

该范式常量（`module_registry.py:550-581`）以五组连线清单给出标准 PDH 拓扑：信号生成链（累加器 → 三角函数）、误差信号链（三角函数余弦输出 → 混频器参考端，探测器信号 → 混频器信号端）、反馈链（混频器 → PID → 累加器误差输入）、状态机控制（PDH 状态机的三路复位控制分别门控 PID、混频器与累加器，累加器快速输出回授状态机的扫描输入）、输出监测（累加器与 PID 输出接至 DAC 通道）。

注入该范式的理由是：PDH 锁定是本系统的主要应用场景，其拓扑在领域内固定且端口对应关系琐碎易错。将其作为参考清单写入提示词，使模型在处理最常见请求时有确定依据，而不必从端口语义逐步推断。这本质上是以领域知识换取可靠性——代价是提示词与范式耦合，若硬件端口分配变更，该常量须同步更新。

## 7.5 生成层：模块代码生成

### 7.5.1 生成流程

`generate_module` 工具针对的场景是：用户需要的模块类型在系统中不存在。`CodeGenerator.generate` 接收模块名、显示名、描述、输入输出端口列表与参数列表，产出六类文件：

| 序号 | 产物 | 位置 |
|------|------|------|
| 1 | VHDL 运算内核骨架 | `modules/<name>/<name>.vhdl` |
| 2 | VHDL 模块封装（总线接口 + 参数 RAM） | `modules/<name>/module_<name>.vhdl` |
| 3 | Python 硬件类 | `generated/hw_classes.py` |
| 4 | Python 节点类（`NodeItem` 子类） | `generated/node_classes.py` |
| 5 | 参数模式 | `generated/schemas.py` |
| 6 | 端口分配记录 | 端口映射文件 |

生成过程中有两项自动推导。其一是参数 RAM 深度：按参数个数向上取到不小于 8 的 2 的幂，再乘 32 位得到总位宽，与第四章 4.2.2 节的参数 RAM 结构对应。其二是端口号分配：`_alloc_ports` 依据输入输出的信号类型分别在数据通道与布尔通道的端口空间中分配编号，并持久化记录以避免重复占用——这直接对应第五章路由矩阵的端口编号体系。

### 7.5.2 运行时注册

`register_runtime` 以运行时打补丁的方式将生成的模块注入正在运行的应用：向 `module_factory` 字典登记节点类、扩展端口号解析函数、更新组件面板。这使新生成的 Python 侧模块无需重启即可用于 `create_module`。

### 7.5.3 能力边界

必须明确该功能的局限，否则容易对其能力产生误解。

**生成的 VHDL 内核是骨架而非实现。** 代码生成器的返回值中显式包含这一说明：实体声明、端口定义、参数 RAM 接口、输入输出缓冲与总线封装完整且可综合，但 `use_input_buffer` 与 `use_output_buffer` 之间的信号处理主体留空，须由硬件工程师填写。换言之，生成器自动化的是模块的**外壳与接口**——这部分在本系统中高度模式化（第六章 6.2 节所述的"内核 + 总线封装 + 参数 RAM"统一骨架），因而适合模板化生成；而算法主体涉及定点格式选择、流水线划分与时序收敛，不是模板所能覆盖的。

**新模块需要重新综合才能真正可用。** 运行时注册仅使 Python 侧的节点类生效，画布上可以放置该模块、可以连线、可以设参数，但 FPGA 中并不存在对应的硬件逻辑。真正可用须经填写内核、重新综合实现、下载比特流三步。因此该功能的实际价值在于**加速模块开发的样板代码环节**，而非实现"自然语言直接生成可运行硬件"。

这一界限划分是客观的：当前的代码生成能力尚不足以自动产出正确的高速定点信号处理逻辑，强行声称其可以只会导致论文结论与实际能力脱节。

## 7.6 可靠性边界的综合讨论

将前几节的机制汇总，可以看出智能体层的安全性并非依赖单一措施，而是由多道约束叠加构成。按模型输出的流经顺序：

| 层次 | 约束机制 | 阻止的失效 |
|------|---------|-----------|
| 接口层 | 工具 JSON Schema 的 `required` 与类型声明 | 参数缺失、类型错误 |
| 工具层 | 统一异常捕获，错误转结构化返回 | 异常穿透至事件循环 |
| 工具层 | `clear_canvas` 显式确认 | 误清空画布 |
| 隔离层 | 节点存在性与端口索引范围校验 | 越界访问、空引用 |
| 隔离层 | 输入端口独占性检查 | 多驱动冲突 |
| 隔离层 | 仅暴露画布操作，无串口直通 | 绕过协议层的任意硬件写入 |
| 既有层 | 信号类型检查（第六章 6.4.2 节） | 物理含义错误的连线 |
| 既有层 | 实例数上限（`_alloc_index`） | 超出硬件可用模块数 |
| 编排层 | 迭代上限 15 轮 | 不收敛的工具调用循环 |

其中最关键的两条是门面的能力边界与既有类型检查的继承。前者确保模型的影响范围被限制在画布编辑，后者确保自动化没有以牺牲既有安全机制为代价。合起来，模型在最坏情况下能造成的后果是**画布拓扑不符预期**——而这是用户可见、可撤销、且不会损坏硬件的。

仍需指出两处尚未解决的薄弱环节。其一，`set_parameter` 的参数值校验依赖各节点类的 `set_params` 实现，智能体层本身不做范围检查，若某模块的实现对越界值未作防护，模型可能写入非法参数。其二，门面的 `create_node` 在参数应用失败时静默忽略异常（`canvas_bridge.py:79-82`），这会使"模块已创建但参数未生效"的状态对模型不可见，可能导致后续推理建立在错误前提上。两者均建议改进，后者的修正尤为直接：将参数应用结果并入返回字典即可。

## 7.7 本章小结

本章介绍了位于系统最顶层的智能体辅助设计层，其目标是把第五章路由矩阵赋予的运行时可重构能力，经自然语言接口转化为实际的实验效率。

该层以五个层次组织约 3300 行代码：交互层提供聊天面板；编排层在后台线程中执行 ReAct 式函数调用循环，以 15 轮迭代上限约束开销；接口层采用 OpenAI 兼容协议以保持服务端中立；工具层以九个工具声明智能体的全部操作能力，并将所有失败转为可据以纠正的结构化错误返回；隔离层以 `CanvasBridge` 门面承担 JSON 与 Qt 对象间的类型转换及全部前置校验。知识层以三个字典描述 12 个基础模块、2 个复合模块与 2 个常量节点，并内置标准 PDH 拓扑范式作为最常见请求的确定依据。生成层可为新模块产出六类文件的样板代码。

架构上有两点值得强调。其一是**纯增量集成**：全部功能以旁挂方式接入，未修改第六章任何既有代码，可独立启用或禁用，故障时可无损回退。其二是**约束叠加而非替代**：智能体继承了既有的信号类型检查与实例数上限，并在其上叠加参数校验与迭代限制，自动化没有以削弱安全机制为代价。九道约束合起来将模型的最坏影响限定为"画布拓扑不符预期"这一用户可见且可撤销的后果。

同时明确了两处能力边界：代码生成产出的 VHDL 仅为接口完整的骨架，算法主体仍需人工填写，且新模块须重新综合方能真正可用；参数值校验与创建时的参数应用失败处理仍有待加固。

本章的功能验证实验安排于第九章 9.2 节。
