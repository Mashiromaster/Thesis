# 第三章 平台架构与设计方法

本章是全文方法论的核心。前两章确立了需求与理论基础：微纳光学实验需要低延迟、可重构、可自动化的实时反馈控制，而反馈控制的理论约束指向"以尽可能低的延迟实现尽可能复杂的信号处理"这一核心矛盾。本章回答的问题是：**如何组织一个 FPGA 平台的内部结构，使其既能满足上述实时性约束，又能在不重新综合的前提下服务于形态各异的实验需求。**

这一问题的答案不在于某个具体模块的实现技巧，而在于平台的组织原则。因此本章先给出设计哲学与分层结构（3.1 节），再依次展开三项支撑该结构的具体机制：模块设计范式（3.2 节）、总线契约（3.3 节）与运行时可重构的实现原理（3.4 节），最后说明平台的扩展流程（3.5 节）。各具体模块的算法实现见第五章，建立在本章机制之上的两类实验应用见第六章。

## 3.1 设计哲学与分层结构

### 3.1.1 从专用系统到通用平台

一个自然的设计思路是针对具体实验编写专用的 RTL 代码：需要 PDH 锁定就实现一条"ADC → 混频 → 滤波 → PID → DAC"的流水线，需要双梳锁定就另写一条包含相位解算与本振校准的流水线。这种做法在单一实验场景下最为直接，资源占用也最紧凑。

但它存在一个根本缺陷：**信号处理模块与它们之间的连接关系被耦合在同一份代码中**。任何拓扑调整——在 PID 前增加一级滤波、把解调方式从乘法混频改为 CORDIC 解算、将两路误差信号交叉耦合——都需要修改 RTL 并重新综合。而一次中等规模设计的综合与实现耗时数十分钟乃至数小时，这与实验现场反复试错的节奏完全不匹配。第一章 1.2 节指出，这正是现有开源方案的共同局限。

本平台的设计哲学因此可以概括为一句话：**把"有哪些运算单元"与"它们如何连接"彻底分离**。前者在综合时一次性固化，后者留给运行时的寄存器配置决定。形式化地说，若记平台固化的模块集合为 $\mathcal{M}$，模块间的连接关系为映射 $\sigma$，则传统专用设计中二者绑定为单一实现：

$$
\text{专用设计}: \quad (\mathcal{M}, \sigma) \xrightarrow{\text{综合}} \text{比特流}
$$

而本平台将其解耦：

$$
\text{平台设计}: \quad \mathcal{M} \xrightarrow{\text{综合}} \text{比特流}, \qquad \sigma \xrightarrow{\text{寄存器写入}} \text{运行时可变}
$$

这一分离带来的改变是**实验范式层面的**：拓扑从设计时的常量变成了运行时可探索的变量。同一套比特流可以在数毫秒内从 PDH 锁定构型切换为双梳锁定构型，使"同一套硬件验证多种控制方案"成为可能。代价是资源消耗——固化全部模块意味着即使当前实验只用到其中几个，其余模块仍占据芯片面积；而互联网络的开销随端口数平方增长。3.4.3 节将定量讨论这一代价。

### 3.1.2 四层结构

依据上述哲学，平台在纵向上划分为四个层次，层间以明确的契约衔接。

```
┌──────────────────────────────────────────────────────┐
│  应用层   PDH 状态机 / SCALO 状态机 / 实验脚本        │
│           职责：实验逻辑与自动化决策                   │
├──────────────────────────────────────────────────────┤
│  运算层   PID / FIR / IIR / CORDIC / 混频器 / 累加器  │
│           职责：定点信号处理，统一模块范式             │
├──────────────────────────────────────────────────────┤
│  互联层   信号路由矩阵（64×64 双套全交叉）             │
│           职责：运行时可配置的模块间连接               │
├──────────────────────────────────────────────────────┤
│  接口层   UART / 自定义并行总线 / SPI                 │
│           职责：参数配置与器件初始化                   │
└──────────────────────────────────────────────────────┘
```

四层的职责边界是清晰的：接口层只负责"把参数送到正确的寄存器"，不理解参数的物理含义；互联层只负责"把数据从端口 A 搬到端口 B"，不理解数据的语义；运算层只负责"对输入做确定的数学变换"，不知道自己处于怎样的信号链路中；应用层则负责把前三层组织为一个有物理意义的实验。

这种划分的价值在于**变更的局部性**。新增一种实验（如第六章的双梳锁定）只需在应用层增加一个状态机，运算层、互联层与接口层完全不变；新增一种滤波器只需在运算层按范式添加模块，其余三层不变。平台因此具备了在不破坏既有功能的前提下持续演进的能力。

值得注意的是，本章的四层结构与第七章上位机软件的四层结构是**不同的分层**：前者是 FPGA 片内的硬件组织，后者是主机侧软件的组织。二者在接口层相接——上位机的协议层发出的 ASCII 命令帧，正是被 FPGA 接口层解析的对象。

### 3.1.3 以数据流为中心的抽象

平台的核心抽象是**数据流图**：每个运算模块是图中的一个节点，模块间的连线是有向边，数据沿边以每时钟周期一个采样点的速率流动。这一抽象之所以适合微纳光学的实时控制场景，有三个原因。

其一，物理对应性。实验者在光学平台上思考问题的方式本就是"信号从探测器出来，经过解调，送进控制器，驱动执行器"——这是一个数据流图。使图形界面的画布拓扑直接对应硬件配置（第七章 7.4 节），意味着界面操作与物理直觉之间不存在翻译损耗。

其二，流水线友好。数据流图中的节点天然可以流水化：每个模块只需在固定延迟后给出结果，不需要知道上下游的时序细节。这使得平台可以在 250 MHz 的高时钟下工作，而各模块的内部流水线深度可以独立选择。

其三，延迟可加性。在纯数据流（无反馈）的路径上，总延迟等于各模块延迟之和加上路由级延迟。这使得第二章的延迟约束 $f_{UGF} \le 1/(8\tau)$ 可以直接用于指导拓扑设计——实验者可以在搭建拓扑时就估算出环路带宽上限，而不必等到实测。第五章 5.3.2 节给出各模块的延迟清单正是为此。

该抽象的边界也需明确：数据流图不直接表达**反馈**。闭环路径在图上表现为一个环，其延迟不可简单相加，稳定性须按第二章的方法分析。平台不阻止用户建立反馈环（反馈正是控制系统的本质），但也不自动验证其稳定性——这是实验者的责任。

## 3.2 模块设计范式

平台的可扩展性依赖于一项约定：**所有运算模块遵循同一架构范式**。该范式固化在 `templates/core_template.vhdl` 与 `templates/module_template.vhdl` 两个模板文件中，新模块由模板派生而来。

### 3.2.1 三段式结构

每个模块由三个部分构成：

| 部分 | 职责 | 对应文件 |
|------|------|---------|
| 运算内核 | 实现模块的数学功能 | `<name>.vhdl` |
| 总线封装 | 解析总线命令，提供参数与控制接口 | `module_<name>.vhdl` |
| 参数 RAM | 以影子寄存器保存参数，支持原子更新 | `parameter_ram.vhdl`（公用） |

分离的理由是**关注点隔离**：内核的作者只需关心定点运算与流水线，不必重复实现总线协议解析；而总线协议的任何改动也不会波及各内核。参数 RAM 作为公用模块被所有模块实例化，其影子寄存器机制（3.3.3 节）因而对全平台一致生效。

内核的端口构成是统一的：

```vhdl
entity <module_name> is
    generic(
        io_buf : buf_type := buf_for_io
    );
    port(
        clk             :   in  std_logic;
        rst             :   in  std_logic;
        core_param_in   :   in  std_logic_vector(<size> - 1 downto 0);
        -- data flow ports
        -- control ports
        auto_reset_in   :   in  std_logic
    );
end entity <module_name>;
```

其中 `core_param_in` 是参数 RAM 的全部内容以单一向量形式送入内核——内核以切片方式取用所需字段。这一设计使参数的位域划分成为内核的内部知识，总线封装无需了解。

### 3.2.2 可配置 IO 缓冲：延迟与时序的显式权衡

范式中最具平台特征的设计是 `io_buf` 泛型。它取自枚举类型

```vhdl
type buf_type is (buf_for_io, buf_i_only, buf_o_only, buf_none);
```

分别表示"输入输出均加寄存器"、"仅输入加"、"仅输出加"、"均不加"。模板以 VHDL 的条件生成语句实现这四种构型：

```vhdl
use_input_buffer : if io_buf = buf_for_io or io_buf = buf_i_only generate
    ...（寄存器化的输入）
end generate;
no_input_buffer : if io_buf = buf_o_only or io_buf = buf_none generate
    ...（直通的输入）
end generate;
```

这一机制的意义需结合第二章的延迟约束理解。每级寄存器为模块增加一个时钟周期（4 ns）的延迟，但同时缩短组合逻辑路径、改善时序裕量。二者的权衡没有普适的最优解：对于处在闭环反馈路径上的模块，延迟直接压缩控制带宽，应尽量取 `buf_none`；对于处在开环监测路径上的模块，延迟无害，取 `buf_for_io` 以换取时序裕量。

把这一权衡**提升为模块的泛型参数**，意味着同一份内核代码可以在不同实例上采用不同的延迟—时序取舍。平台因此得以在关键路径上追求极低延迟，而在非关键路径上保持时序收敛的余量，无需维护两份代码。这是"延迟作为一等设计变量"这一理念在代码层面的体现。

### 3.2.3 自动复位契约

范式的第三项约定是复位语义：

```vhdl
internal_rst <= '1' when rst = '1' or
                (enable_auto_reset = '1' and auto_reset_in = '1') else '0';
```

模块的内部复位由两个来源合成——来自总线的全局复位 `rst`，以及来自其他模块的 `auto_reset_in`，后者受参数 `enable_auto_reset` 门控。

这一契约是**跨模块协同的基础**。应用层的状态机需要在特定时刻复位运算模块：PDH 状态机在扫描阶段须保持 PID 处于复位以防止积分器累积无意义的误差，捕获瞬间再释放复位使 PID 接管（第五章 5.2 节）。若没有统一的自动复位契约，这类协同须为每对模块单独布线；有了该契约，状态机只需把复位信号送入布尔路由矩阵，再配置到目标模块的 `auto_reset_in` 端口即可——**复位也成为一种可路由的信号**。

`enable_auto_reset` 的门控作用则保证了该机制的可选性：不参与自动流程的模块可将其置零，从而忽略一切外部复位请求。

## 3.3 总线契约

接口层的核心是一套自定义并行总线。本节说明其设计选择，其中 3.3.3 节的影子寄存器机制是平台"参数原子更新"能力的硬件基础。

### 3.3.1 寻址方案

总线采用二级寻址：6 位模块选择信号可寻址至多 64 个模块，7 位地址在模块内部选择 32 位参数字。`Top.vhdl` 当前实例化了 34 个模块，为扩展留有余量。

选择并行总线而非 AXI 等标准接口的理由是**延迟与资源**。标准总线为通用性引入了握手、突发传输、仲裁等机制，而本平台的参数配置具有明确特征：写操作远多于读操作、无需突发、单一主控、对吞吐无要求但对解码逻辑的面积敏感。自定义总线因而可以极简：34 个模块的解码只需一级比较器。

### 3.3.2 分层命令编码

命令字采用分层编码而非平坦编码——先以高位字段区分命令大类（总线读写、模块控制、SPI 事务等），再在类内以低位字段区分具体操作。这一安排降低了解码逻辑的深度：中央控制状态机只需先对大类做一次判决，再在相应分支内做二次判决，而非对全部命令做一次宽比较。在 250 MHz 时钟下，解码路径的逻辑级数直接影响时序收敛，分层编码因此是一项必要的优化。

### 3.3.3 影子寄存器与原子更新

平台面临一个由数据宽度不匹配引起的问题：总线一次传输 32 位，而许多参数宽于 32 位——64 位 DDS 频率控制字、64 个 FIR 系数、IIR 的 11 个系数。若逐字写入且每字立即生效，参数在更新过程中将经历中间状态。对于运行中的闭环系统，这意味着滤波器会在数个时钟周期内以"新旧系数混合"的非法构型工作，可能产生输出跳变甚至发散。

解决方案是参数 RAM 的**影子寄存器**结构，配合总线的 `WRITE_HOLD` 命令。写入时，数据先进入影子寄存器而不影响内核；`HOLD` 标志置位的写操作只更新影子，清零的写操作则在更新影子的同时将全部影子内容一次性提交至工作寄存器。于是一个 $N$ 字参数的更新序列为：前 $N-1$ 字以 `HOLD` 写入，第 $N$ 字正常写入并触发提交。内核看到的是**单次原子切换**，不存在中间状态。

这一机制贯穿三个层次：硬件的影子寄存器提供能力，总线的 `WRITE_HOLD` 命令提供控制手段，上位机的间接参数机制（第七章 7.2.2 节）将其封装为对用户透明的物理量赋值。三者协同是本平台软硬件协同设计的典型例证——任一层单独都无法实现该功能。

### 3.3.4 可靠性设计

总线之上的 UART 链路采用三重错误检测：硬件偶校验、完整命令回显、`:ACKN` 应答。三者检测的失效模式不同——偶校验捕获单比特误码，回显校验捕获多比特误码与帧错位，应答校验则确认命令在逻辑上被成功执行（地址合法、参数有效）。

这一设计针对的是实验环境的实际条件：光学实验室中存在大量开关电源、射频源与高压驱动器，串行链路的误码率不可忽略。而参数配置的错误往往难以察觉——一个被误码破坏的滤波器系数不会使系统崩溃，只会使其行为偏离预期，在实验中表现为难以归因的异常。三重检测使此类错误在发生时即被捕获，而非在数据分析阶段才被怀疑。

## 3.4 运行时可重构的实现原理

本节说明平台最具特征的机制：信号路由矩阵。其模块级实现细节见第五章 5.1 节，此处讨论的是设计原理与代价。

### 3.4.1 全交叉结构

互联层由两个相互独立的 $64\times64$ 全交叉开关构成，分别承载 16 位数据信号与 1 位布尔控制信号。任一输入端口可被连接至任意数量的输出端口，连接关系完全由寄存器决定。

数据与控制分离是一项有意的设计。二者的特征截然不同：数据信号为 16 位、持续流动、关注延迟与截断；控制信号为 1 位、事件性、关注边沿与时序关系。若混用同一套矩阵，16 位的通路承载 1 位信号将浪费 15/16 的资源。分离后，布尔矩阵的资源开销仅为数据矩阵的 1/16，却使"复位、使能、触发"等控制信号获得了与数据同等的可路由性——这正是 3.2.3 节自动复位契约得以成立的前提。

每个输出通道由一个 8 位配置字描述：6 位指定源端口编号，1 位使能，1 位保持。

### 3.4.2 无扰动切换

配置字中的保持位解决了一个实际问题：在运行中的闭环系统上改变路由时，若输出在切换瞬间出现毛刺，该毛刺将作为扰动注入控制环路，可能导致失锁。保持位置位时输出冻结于当前值，待新配置写入完毕后再释放，从而使拓扑切换对下游不可见。

这一能力的实验价值在于：**拓扑调整可以在不中断锁定的情况下进行**。例如在已锁定的 PDH 环路上插入一级额外的低通滤波以抑制高频噪声，若切换过程产生毛刺则必然失锁并需重新捕获；有了保持位，该操作可以平滑完成。

### 3.4.3 资源代价与设计权衡

全交叉结构的资源消耗随端口数平方增长。对 $N$ 个端口、位宽 $W$ 的矩阵，所需的选择逻辑规模约为

$$
\text{资源} \propto N^2 \cdot W
$$

当前 $N = 64$、数据矩阵 $W = 16$，使路由矩阵成为全系统最大的单一资源消耗项与主要布线压力来源，源码中以 `max_fanout` 约束做针对性优化。

这一代价是否值得，取决于平台的定位。对于固定功能的产品，它显然不值得；对于需要反复探索控制方案的科研平台，它换来的是实验迭代速度的数量级提升。若未来需要扩展至更多端口，平方增长将变得不可接受，此时应考虑多级交换网络（如 Clos 网络）——以少量额外延迟换取资源从 $O(N^2)$ 降至 $O(N\log N)$。该权衡在第十章作为改进方向讨论。

### 3.4.4 未连接语义、VOID 约定与扇出

**未连接的硬件语义。** 配置字的使能位（bit 6）为零时，该输出通道被置零而非保持悬空：

```vhdl
if control(i * 8 + 6) = '0' then
    sig_out_buf(i) <= (others => '0');
```

这一设计使"未连接"成为一个确定的状态而非未定义行为，接入未使能通道的下游模块读到的是零而非随机值。对于定点数据通路，零是一个安全的默认值——它不会使积分器累积虚假误差，也不会在滤波器中激起瞬态。

**VOID 约定。** 在此硬件语义之上，上位机侧进一步约定端口 0 为 `VOID`：

```python
VOID = 0      # Signals to port 0 are ignored. Signals from port 0 are always zero.
VOID_BOOL = 0 + 64
```

需要明确的是，这是一项**软件层的编号约定**（`python control/port_numbers.py:3-4`）而非 RTL 中的特殊逻辑——路由矩阵本身不对端口 0 做特别处理。该约定的作用是为上位机与图形界面提供一个统一的"空"端口语义，使未连接的输入在配置数据结构中有确定的表示，无需引入额外的可选类型。布尔矩阵的 VOID 编号为 64，与数据矩阵的编号空间相区分。

**扇出。** 矩阵天然支持单输出多扇出：由于每个输出通道独立选择其源端口，同一个源端口可被任意多个输出通道同时选择。这在实验中对应"同一信号既送入控制环路又送往监测通道"的常见需求，无需额外的分路模块。其代价由布线压力承担——这也是 `Top.vhdl` 对总线信号施加 `max_fanout` 约束的原因之一。

## 3.5 平台的扩展流程

平台的生命力在于可扩展性。依据前述范式，新增一个运算模块的完整流程如下：

1. **由模板派生内核**。复制 `core_template.vhdl`，填入模块名、参数 RAM 深度与数据流端口，在 IO 缓冲块之间实现运算主体。
2. **由模板派生总线封装**。复制 `module_template.vhdl`，确定参数 RAM 的位宽与参数的位域划分。
3. **在 `Top.vhdl` 中实例化**，分配模块编号，将数据端口接入路由矩阵的相应端口、控制端口接入布尔矩阵。
4. **在 `mypak.vhdl` 中登记**模块的总线地址常量。
5. **编写上位机硬件类**，继承 `ModuleBase`，声明参数字典与物理量换算（第七章 7.2 节）。
6. **编写图形界面节点类**，声明端口的信号类型与参数模式（第七章 7.4 节）。

六个步骤中前四步属硬件、后两步属软件，且各步骤的接口均由范式固定。这一流程的高度模式化正是第八章代码生成工具得以自动产出样板代码的前提——该工具可自动完成第 1、2、5、6 步的框架部分，而第 1 步中的运算主体（涉及定点格式选择与流水线划分）仍需人工填写。

需要指出流程中的一项**人工维护负担**：模块的端口定义在硬件侧（`Top.vhdl`）与软件侧（界面节点类、模块知识库）各有一份，须保持一致。不一致不会引起综合错误，但会导致界面连线与实际硬件路由不符，是一类隐蔽的故障来源。第十章将其列为改进方向。

## 3.6 本章小结

本章给出了平台的设计方法论，核心是一条组织原则：**把"有哪些运算单元"与"它们如何连接"彻底分离**，前者综合时固化，后者运行时可配。由此平台在纵向上划分为应用层、运算层、互联层、接口层四层，层间契约明确，使任一层的变更不波及其余层。

支撑该结构的三项机制分别解决三类问题。模块设计范式解决**一致性与可扩展性**：三段式结构分离运算与协议，可配置 IO 缓冲将"延迟与时序裕量的权衡"提升为模块泛型，自动复位契约使控制信号与数据同等可路由。总线契约解决**配置的正确性**：二级寻址与分层命令编码在满足配置需求的前提下最小化解码延迟，影子寄存器配合 `WRITE_HOLD` 命令实现超宽参数的原子更新，三重错误检测应对光学实验室的电磁环境。路由矩阵解决**运行时重构**：数据与布尔双套全交叉使拓扑成为寄存器状态，保持位使切换过程无扰动，代价是资源随端口数平方增长。

平台的核心抽象是数据流图，它与实验者的物理直觉同构、与流水线实现相容、且使环路延迟可加从而让第二章的带宽约束可直接用于拓扑设计。该抽象的边界在于不自动验证反馈环的稳定性，这仍是实验者的责任。

本章确立的范式是后续各章的共同基础：第五章的各运算模块均按 3.2 节范式实现，第六章的两类实验应用均建立在 3.4 节的可重构机制之上，第七、八章的软件与智能体层则是 3.5 节扩展流程中软件侧步骤的系统化。
